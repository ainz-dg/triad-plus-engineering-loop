## Summary

This release updates the terminal first-run experience for selecting a
Control Workspace, explicitly mapping product repositories, and installing
one or more registered adapters in a reviewed setup plan. It also records an
integrated local-only smoke for selecting and installing all six adapters in
one pseudo-terminal session. The release delta also adds path- and
assignment-bound visibility for assigned attempt evidence in the read-only
Cockpit and refreshes the OpenCode quickstart for separate control and product
repositories.

This is onboarding and installation inventory work. It does not add new Core
behavior, host-native discovery, or per-Attempt adapter selection or dispatch.
Installing multiple adapters does not route an Attempt between harnesses.

## New-workspace onboarding

Running `npx triad-plus` without a registered installation in the current
directory defaults to **New workspace**; a valid manifest defaults to
**Manage existing**. The wizard does not search sibling directories. For new
setup it asks for a separate Control Workspace root. A Control Workspace can
be non-Git while mapped product repositories are independent Git roots; a
Control Workspace inside a Git root is refused rather than repurposing or
migrating that repository.

Repository mapping is an explicit choice:

- **Existing:** select local Git repositories and declare each ID, path, base
  branch, project branch, and worktree. Read-only immediate-child suggestions
  are not selected automatically.
- **Greenfield:** select empty paths to initialize as local Git repositories
  only after approval. No remote is created and nothing is pushed.
- **Defer:** skip mappings; setup may install assets but remains **NOT READY**
  until the required repository and project inputs exist.

The wizard does not clone from a URL or search sibling directories. It can
select several of the six registered adapters in one session. An optional
team identity/model configuration may also be requested. A preview names the
exact Control Workspace, repository mapping, project-local files, and
readiness result. Only the exact `install` confirmation applies that plan.
Global/user-level host files, credentials, and account settings are not
written.

The preview is read-only. Unsafe paths, a Control Workspace under a product
Git root, or preflight conflicts stop setup. Relevant root, role-configuration,
mapping, ownership, and collision conditions are checked before or during
application; changed inputs are not silently overwritten. If a later adapter
installation fails, earlier successful steps are retained and reported rather
than automatically deleted; inspect the partial installation before retrying.
This is not a transactional rollback.

Installation does not establish Triad readiness. The post-setup readiness
check reports missing root `PRD.md`, `.loop/quality-gates.yaml`, initial Git
commits, and mapped worktrees; setup does not create these implicitly. In
particular, a greenfield `git init` is not an initial baseline commit.

## Existing-workspace management and scriptable CLI

An already registered workspace follows the management path rather than
first-run onboarding. The wizard offers list, add, doctor/status, upgrade,
remove, and exit. `init` refuses to overwrite a registered installation;
`upgrade --apply` is the managed update/repair path for an existing workspace.
Existing scripts can continue to use the CLI commands, including
`init`, `adapter add`, `doctor`, `version`, `upgrade`, and
`uninstall`; the terminal wizard does not replace those interfaces.

The schema-v2 adapter inventory records project-local membership and managed
asset ownership. It does not select a host for an Attempt, provide
per-Attempt multi-harness dispatch, or imply that a host can discover or invoke
the installed files. The read-only Cockpit can expose assigned attempt
verification documents only after their declared attempt path and
assignment/evidence identity bindings validate; this does not open general
filesystem access to arbitrary evidence paths.

## Package and verification boundaries

The release requires Node.js **>=20** and declares **zero runtime
dependencies**. The first-install smoke used a non-Git Control Workspace and a
separate direct-child Git repository, selected all six adapters in one TUI
session, approved one project-only installation plan, and checked the
schema-v2 manifest plus read-only `adapter list` and `adapter doctor`
results. This is a local artifact/install smoke, not six native-host tests.

**Native discovery and invocation are NOT VERIFIED** for the installed host
entries. In particular, the current evidence does not establish the Codex
user-level prompt contract from this non-Git Control Workspace or a Hermes
entry installed in a user profile. The local-only smoke intentionally made no
global writes. Adapter presence is not evidence of native host recognition.

Attempt-bound multi-harness dispatch is **NOT SUPPORTED**. No claim is made
that an Attempt can choose or route to a harness based on this installation.
M1B traceability remains a separate audit stream. Ketchup2 benchmark work
remains stopped for leakage review and is outside this release.

The release package smoke verified the published npm artifact and the published
GitHub tag was resolved to the same commit shown above. These checks confirm
publication identity; they do not expand the feature or host-compatibility
claims in this document.
